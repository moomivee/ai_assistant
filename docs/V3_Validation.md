## Проверка выбора сорта для прогноза

В пользовательском трейсе от 18 ноября план содержал `benchmark="Brent"` для запроса о цене Urals с дисконтом к Brent. В отдельном диалоге, где пользователь задал дисконт второй репликой, расчёт прошёл. Эти два запроса должны привести к одному набору аргументов калькулятора.

Для проверки запущенного стенда с настроенной моделью выполните из корня проекта:

```bash
python3 -m eval.forecast_smoke --base-url http://127.0.0.1:8003
```

Проверка обращается к API приложения и использует настроенный в нём провайдер. Она сверяет фактически переданные параметры, число расчётов, прогнозные месяцы и интервалы. В набор входят две формулировки для Urals, диалог с уточнением, обычные прогнозы Brent и WTI и запрос о WTI с дисконтом. Для каждого обращения выводится `trace_id`, по которому можно разобрать результат. Автоматические тесты планировщика с заданными ответами модели запускаются отдельно.

Для проверки именно памяти запустите два диалога с моделью на своём стенде.

```bash
python3 -m eval.forecast_smoke --base-url http://127.0.0.1:8003 --memory-only
```

В первом диалоге горизонт и дисконт для Urals приходят в разных сообщениях. Во втором пользователь успевает исправить горизонт перед расчётом. Проверка сверяет тип и параметры вызванного инструмента с ожидаемыми и выводит идентификаторы трейсов.

## Исправление ссылок на фрагменты, 17 ноября

В запросе «какой нефтью торгует Россия?» (`14109b9533f94d9fbdadf0f513e6e606`) два веб-поиска вернули по шесть результатов. Часть URL повторялась. После каждого поиска модель предложила два утверждения. У каждого хотя бы одна ссылка отсутствовала среди идентификаторов переданных блоков. Приложение отклонило утверждения до смысловой проверки. Сам файл содержит счётчики, поэтому конкретное ошибочное значение ссылки восстановить по нему нельзя. Ещё две попытки повторить последний поиск остановил контроллер.

Теперь схема генерации содержит идентификаторы блоков текущего набора доказательств. Если все утверждения ссылаются на неизвестные блоки, модель может один раз за пользовательский запрос заново сформировать ответ по тем же текстам в пределах общего бюджета времени. Если часть утверждений уже имеет корректные ссылки, они сразу проходят оставшиеся проверки. Приложение проверяет адреса, числа и при включённом review смысл и полноту ответа. В диагностике сохраняются число первоначальных отказов и результат попытки исправления.

На фрагментах из этого экспорта локально воспроизведены оба набора контекста (9 и 15 блоков). При имитации повторной неверной ссылки ни одно утверждение не прошло. В отдельном сценарии с исправленной ссылкой утверждение прошло до смысловой проверки после одного веб-поиска. Проверен формат отправляемой схемы на HTTP-фикстурах GigaChat и OpenAI. Реальный ответ GigaChat после обновления ещё предстоит измерить.

## Дополнение 17 ноября: обзор торговли и объяснение выбора источников

В трейсе `1930c11c7327498b921cae52a40182f6` на вопрос «какой нефтью торгует рф?» модель выбрала **веб**, а не базу знаний. Первый вызов без поискового текста был отклонён; модель исправила аргумент, и `web_search` выполнился за 2202 мс. Итоговый ответ использовал только W4 — короткий поисковый фрагмент страницы «Эталонные сорта нефти» без установленной даты. После `complete=true` граф завершился. Файл не содержит признака выполнения семантического review, поэтому по нему нельзя установить, была ли эта проверка включена.

Проблема относится к покрытию вопроса: цитата о известных маркерных сортах не устанавливает достаточный перечень того, чем страна торгует. Слова «на данный момент» из недатированного источника также не доказывают состояние на дату запроса. Требовать второй поиск формально неправильно: узкий вопрос может быть закрыт одним хорошим фрагментом, а широкий обзор — остаться неполным после нескольких вызовов.

В существующий `CitationReview` добавлены `coverage` (`sufficient`, `partial`, `unverified`) и `missing_aspects`. Нового обращения к модели нет. Для полного ответа нужны достаточный охват и отсутствие конкретных пробелов наряду с прежними проверками утверждений. Пропущенный `coverage` означает `unverified`, а не техническую ошибку или автоматическое одобрение. Глобальное указание «не требуй другие сорта» ограничено вопросами с явно указанными объектами; широкие перечни проверяются по их собственному охвату. Код не содержит списка ожидаемых сортов или обязательного числа источников.

Контроллер передаёт последнюю оценку и недостающие аспекты следующему выбору действия. Модель может открыть страницу, уточнить запрос, сменить тип источника или закончить с ограничением. Вопросы об актуальных поставках отделены в инструкциях от справочных свойств сырья и исторических периодов. В `purpose` запрашивается краткая цель действия и связь источника с задачей; интерфейс показывает это как объяснение модели, не как установленную причину её внутренних решений.

В инспекторе появился видимый блок «Откуда взят ответ»: источники финального ответа, реально выполненные инструменты, отклонённые попытки, цель успешного шага и ограничение «только база знаний». Для использованных веб-источников отдельно указаны неизвестная дата и фрагментарность. Эти сведения видны даже при `status=ok`; предупреждения от неиспользованных источников не подменяют свойства процитированного материала.

Новая диагностика содержит `semantic_review_enabled`, а каждая попытка — `review_enabled`, `review_attempted`, `review_executed`, `candidate_complete`, `coverage` и `missing_aspects`. `review_attempted` отмечает начало обращения, `review_executed` — успешный возврат структурированного результата; так ошибка проверки отличается от её отсутствия. При `ANSWER_SELF_REVIEW=false` текст с утверждениями выдаётся как `partial` с оговоркой о непроверенном смысле и полноте. Если кандидат сформирован и обязательные расчёты/котировки выполнены, запрос завершается с `review_disabled`: новые поиски не смогут включить отключённую настройку. Пустые кандидаты и реальные пробелы исходных данных могут требовать продолжения. Сам по себе внутренний `candidate_complete` или `answer_checks.complete` при выключенном review не является подтверждением качества.

Добавлены [10 dev-регрессий покрытия](../eval/data/coverage_regressions.jsonl): обзор/примеры, полный список документа/выборка, текущие/исторические поставки, свойства/отгрузки, совместный анализ/запрет веба. Это авторская разметка с `human_review=pending`, без готового перечня сортов в эталоне. Граф проверен на маршрутах веб → страница, веб → RAG, RAG → веб и на завершении узкого вопроса после одного поиска. Отдельно проверено сохранение обязательного расчёта при отключённом review. HTTP-фикстуры GigaChat проверяют структурированный контракт; они не измеряют способность живой модели определить достаточный обзор.

Для проверки на аккаунте с ключами установить `ANSWER_SELF_REVIEW=true` и `PROMPT_SOURCE=local`, пересоздать контейнер и повторить исходный вопрос. Отдельный прогон набора:

```bash

  --data eval/data/coverage_regressions.jsonl \
  --judge \
  --output .cache/eval/coverage-v3-live.json
```

Наличие веб-вызова в данном трейсе удовлетворяет маршрутизационной политике. Его качество оценивается по содержанию, периоду и покрытию вопроса. Новый `final_review_consistency` также отклоняет `ok`, противоречащий явному `coverage` или отключённой проверке; отсутствие этих полей в историческом трейсе не доказывает успешный review.

Локально пройдено **525 Python-тестов**, один тест русского OCR пропущен из-за отсутствующего языкового пакета. Пройдены Ruff, форматирование, синтаксис JavaScript и валидация датасетов. Браузерные фикстуры дополнены веб-маршрутом без RAG, отказами, объяснением области поиска и оговорками только для используемых источников; выполнение вынесено в CI. Эти результаты не являются долей корректных ответов живого GigaChat.

## Дополнение 17 ноября: границы темы и пустой результат проверки

Трейс `d207257b889a426aafb12a44ef749cee` относится к вопросу «какая зарплата у нефтегазового аналитика?». Дата запроса передана правильно; технической ошибки GigaChat или инструмента в этом запуске нет. План ошибочно отнёс карьерный вопрос к исследованию нефтегазового рынка. Веб вернул шесть нерелевантных источников ЦБ и ЕС. Повтор с другой глубиной дал те же источники, следующий одинаковый вызов был отклонён, после чего сработала остановка без прогресса. Выдуманной зарплаты в финальном ответе нет, однако агент потратил шаги на задачу вне своей роли.

Уточнён смысловой мандат планировщика: личная зарплата, вакансии и резюме относятся к `outside`; трудовые затраты, дефицит кадров и забастовки как факторы добычи, себестоимости или поставок относятся к `research`. Решение принимает LLM. Код нормализует уже выбранный `outside` и завершает запрос без инструментов; списков запрещённых слов или дополнительного классификатора нет. Инструкция выбора действий отдельно поясняет, что новизна текста не доказывает его полезность, а переключение глубины того же нерелевантного поиска не заменяет содержательного уточнения запроса.

В старом трейсе `claims=0` и общее сообщение проверки не позволяют установить, предложила ли модель пустой список фактов или проверка отклонила её утверждения. Теперь `answer_checks.validation` сохраняет число предложенных утверждений, отказы по ссылкам, числам и смыслу, число принятых утверждений и стадию/причину. Пустая генерация получает отдельную причину `no_candidate_claims`. При исключении видно, на какой стадии оно произошло. Исходные отвергнутые тексты в эти счётчики не записываются; дополнительных обращений к модели нет.

Источники веб-поиска отмечаются `provider` и `cache_hit`, которые видны в инспекторе. В старом файле задержки 1–2 мс и более ранний `retrieved_at` совместимы с попаданием в кэш, но явного признака кэша в нём нет. Кэш сохраняет исходное время получения: повторное чтение не делает публикацию свежей.

Добавлен набор [scope_regressions.jsonl](../eval/data/scope_regressions.jsonl): 14 авторских dev-вопросов, семь пар с похожими словами и разными целями. Проверки с HTTP-фикстурами подтверждают исполнение решения `outside` без инструментов и возможность веб-поиска для профильного вопроса о затратах. Это не измеренная точность классификации живого GigaChat; разметка имеет `human_review=pending`. Для проверки на аккаунте с ключами:

```bash
uv run python -m eval.run agent \
  --data eval/data/scope_regressions.jsonl \
  --output .cache/eval/scope-v3-live.json
```

В набор также входят четыре вопроса о границе между справкой и поручением. Прямой вопрос «Что ты можешь?» и просьба привести примеры должны вернуть `capabilities` со статусом `ok` и пустым списком инструментов. Для фразы «Что ты можешь сказать о различиях Urals и ESPO по содержанию серы?» ожидается исследование, а для просьбы составить резюме — ответ о границе специализации. Ещё два сценария проверяют запрос о «рейтинге российской нефти» и последующую реплику «По объёму экспорта сырой нефти за 2024 год». Всего в наборе 20 dev-вопросов. Для неоднозначного рейтинга статус проверяет получение уточняющего вопроса, а метрика маршрута отдельно показывает, удалось ли задать его до поиска.

Оценивать нужно оба вида ошибок: выход за границы роли и отказ на профильный вопрос. Наличие правильного `intent` само по себе не подтверждает качество дальнейшего исследования или ответа.

Локальный прогон после изменения: **498 Python-тестов пройдено, 1 OCR-тест пропущен** из-за отсутствующего русского пакета Tesseract. Пройдены ruff, форматирование, синтаксис JavaScript и валидация основного набора из 100 вопросов. Отдельные регрессии проверяют передачу счётчиков до экспортируемого трейса и сохранение исходного `retrieved_at` при чтении поисковых результатов и страниц из кэша. Браузерная проверка дополнена отображением счётчиков; её выполнение вынесено в CI.

## Дополнение — пустой ответ GigaChat, 16 ноября 2026

Пользовательский запуск на Mac подтвердил сборку контейнера, TLS/авторизацию и доступность `GigaChat-2`. Затем вопрос о последней встрече ОПЕК+ воспроизвёл сбой: план получен, RAG вернул шесть фрагментов, но `CitedAnswer` пришёл пустой строкой с `finish_reason=stop` и 2 выходными токенами. Веб-поиск не успел выполниться. Причина пустой генерации внутри провайдера не установлена.

Добавлена одна резервная JSON-генерация с локальной проверкой исходной схемы, общим лимитом времени и отдельной диагностикой попыток. Исправлены статус ответа и корневого трейса при технической ошибке после retrieval. Найденные фрагменты без готового ответа больше не означают `partial`.

Регрессии используют HTTP-фикстуру наблюдавшегося пустого ответа: восстановление, повторный пустой ответ, невалидный JSON по схеме, учёт токенов обеих попыток, защита ключей, общий таймаут, продолжение к выбранному моделью веб-поиску и сохранение уже подготовленного частичного ответа. Это проверка обработки сбоя, не живой eval GigaChat. Реальную успешность резервной генерации и качество ответа после обновления необходимо проверить на аккаунте пользователя.

После исправления: **380 Python-тестов пройдено, 1 пропущен** из-за отсутствующего русского языкового пакета Tesseract в текущем окружении. `ruff check`, форматирование изменённых файлов и валидация eval-набора (100 вопросов, 40 retrieval) пройдены. Пропущенная OCR-проверка не относится к изменению LLM-клиента; прежний отдельный OCR-прогон описан ниже.

Сам ответ модели в данном файле отсутствует, поэтому конкретное выбранное действие из него не восстанавливается.

В `NextAction` поля `query`, `report`, `page` теперь имеют пустые значения по умолчанию. Проверяются аргументы именно выбранного действия: поисковый текст, зарегистрированный документ и страница/блок, найденный URL. Недостающий аргумент инструмента возвращается в цикл как замечание для исправления, а не как недоступность LLM. Для получения только котировки пустой поисковый текст допустим; при поиске публикаций он отклоняется. Неизвестные поля и запрещённые действия по-прежнему не принимаются.

Добавлены регрессии через настоящий LLM-клиент с HTTP-фикстурами обоих провайдеров, полный переход минимального решения GigaChat к веб-инструменту, исправление аргументов PDF и вызов котировок через Ouroboros. Это проверка контракта и передачи данных; успешный ответ живой модели после исправления ещё требует пользовательского прогона.

### Дополнение 17 ноября: выбор источников, дата и актуальность ответа

В трейсе `bd6477fb7a164a5cb1e38c9c16ec409f` интернет-поиск выполнился, но был ограничен июлем 2025 года. Ответ о «последней встрече ОПЕК+» опирался на библиографию старого отчёта. После отклонения новых утверждений контроллер восстановил прежний черновик с `complete=true`, а само наличие веб-результатов позволило объявить ответ полным. Успешный инструмент не означал успешное решение вопроса.

Обновлённая проверка различает выбор источника, пригодность доказательства и итоговый ответ. Для текущих событий модель может сразу выбрать веб; для вопроса по документу — RAG; для сравнения отчёта с новостями нужны оба источника без обязательного порядка. Запрет веба и выбранная пользователем область документов остаются ограничениями исполнения. В каждый запрос модели передаётся единое время обработки с часовым поясом `APP_TIMEZONE` (по умолчанию `Europe/Moscow`). Дата публикации, дата события и момент загрузки источника не взаимозаменяемы.

Основной eval использует [cases_v3.jsonl](../eval/data/cases_v3.jsonl): те же 100 вопросов, 40 эталонных retrieval-контекстов и прежние dev/test-группы, но явные требования политики `adaptive-v3`. Набор воспроизводится через `python -m eval.build_adaptive_seed`. Старый `cases.jsonl` и результаты прежних прогонов сохранены; их маршрутизационные метрики не следует напрямую сравнивать с новой политикой. Наличие test-разбиения в знакомом наборе не делает его новым слепым тестом.

Добавлены [10 регрессий](../eval/data/adaptive_regressions.jsonl): последнее событие, исторический период, граница отчёта, действующее решение, свойства сортов, составной вопрос, текущая котировка, чистый расчёт, актуальный вопрос с запретом веба и различие состоявшейся/запланированной встречи. Это подготовленные dev-сценарии по известным ошибкам; ручная проверка разметки ещё требуется. Для общего вопроса о свойствах сорта не зашиты единственные допустимые цифры: нужно оценивать соответствие конкретной спецификации и цитате. Точные PDF-контексты отдельно остаются в retrieval-оценке.

| Что измеряется | Как интерпретировать |
|---|---|
| `tool_policy_pass` | Выполнены необходимые инструменты или размеченные альтернативы, соблюдены запреты и открытие веб-страницы после её обнаружения. Это ещё не оценка содержания. |
| `required_tool_success` | Нужные инструменты завершились без технической ошибки. Не означает, что выдача релевантна. |
| `tool_sequence_exact`, `rag_before_web` | Описание маршрута; в `adaptive-v3` не являются критерием качества. |
| `final_review_consistency` | Ответ `ok` не противоречит последней проверке (`complete=true`, без ошибки/отрицательной обратной связи). Не является независимым подтверждением истинности. |
| Retrieval Hit@k, MRR, evidence recall | Качество поиска размеченных контекстов, отдельно от качества ответа и актуальности веба. |
| Judge или ручная оценка | Проверка, что цитаты подтверждают смысл, период, полноту и ограничения ответа. Собственный review той же модели не заменяет независимую оценку. |

Локальные детерминированные проверки подтверждают альтернативные допустимые маршруты, сохранение запрета веба, отсутствие подстройки требований под ошибочный план модели и обнаружение противоречия между финальной проверкой и `status=ok`. Валидация обоих наборов пройдена. Это не результат живого eval GigaChat/Tavily: ключей в окружении разработки нет.

Дополнительно проверены смена дня/года и часового пояса, неизменность времени внутри запроса, восстановление поиска после отклонённой цитаты и отсутствие возврата старого черновика. Контекст распределяется по точным блокам между источниками; новые результаты получают место перед ранее прочитанными материалами. Длинный старый отчёт не должен полностью вытеснять новые веб-фрагменты. В `answer_checks` отдельно сохраняются предложенные источники, реально переданные источники и `evidence_ids`.

Итог этого обновления: **467 Python-тестов пройдено, 1 OCR-тест пропущен** из-за отсутствующего русского языкового пакета Tesseract. Пройдены `ruff check`, `ruff format --check`, валидация 100 основных и 10 новых eval-сценариев, проверка воспроизводимости нового набора и синтаксиса JavaScript. Это результаты компонентов и управляемых регрессий, не доля правильных ответов живой модели.

Тесты интерфейса дополнены проверкой даты запроса. Локальный повтор браузерного прогона заблокирован окружением: Chromium не может создать сокет. Синтаксис JavaScript проверен; успешный браузерный прогон и новые скриншоты для этого изменения не заявляются.

Для существующего `.env` явно установить `ANSWER_SELF_REVIEW=true`, `APP_TIMEZONE=Europe/Moscow` и `PROMPT_SOURCE=local`. Старое значение `false` не заменяется новым значением по умолчанию. Если промпты берутся из Langfuse, требуется отдельно опубликовать и проверить новую версию перед продвижением её label; локальное обновление файлов не меняет удалённые промпты.

После обновления и настройки ключей минимальный живой прогон:

```bash
uv run python -m eval.smoke --output .cache/eval/adaptive-v3-live.json
```

Для повторения старого протокола явно указать `--data eval/data/regressions.jsonl`. `eval.smoke` проверяет контракт, маршрут и согласованность статуса; он не объявляет семантическую актуальность доказанной. Полный прогон с оценкой ответа:

```bash
uv run python -m eval.run agent \
  --data eval/data/cases_v3.jsonl \
  --judge \
  --output .cache/eval/adaptive-v3-agent.json
```

Без отдельного `JUDGE_MODEL` оценщик совпадает с основной моделью, что фиксируется в результатах. Для независимой оценки нужны отдельный калиброванный оценщик (`eval.assess_saved`) и ручная проверка части примеров. Выходной путь каждого прогона должен быть новым, чтобы сохранить предыдущие замеры.

### Дополнение 17 ноября: JSON-схема вместо ответа

Следующая диагностика локализовала ошибку после пустого нативного ответа: резервная генерация вернула JSON с `$defs`, `additionalProperties`, `properties`, но без `claims` и `complete`. Это проверка контракта и обработки ошибок; влияние нового промпта на живую модель предстоит проверить повторным запросом.

## Измеренное качество retrieval

[Полный замер](../eval/results/v3-retrieval-baseline.json): два исходных PDF, 115 прежних чанков, 40 размеченных вопросов (15 dev, 25 test). Сравниваются одинаковый корпус, вопросы и разбиение. `clean_query` — подготовленный поисковый запрос из датасета; `full_question` — исходный вопрос. Запрос, сформированный реальной LLM, может отличаться.

| Эмбеддер и поиск | Запрос | Hit@1 | Hit@5 | MRR@10 |
|---|---|---:|---:|---:|
| MiniLM dense | clean_query | 0,350 | 0,550 | 0,445 |
| MiniLM hybrid | clean_query | 0,300 | 0,600 | 0,400 |
| E5 dense | clean_query | 0,225 | 0,525 | 0,361 |
| E5 hybrid | clean_query | 0,175 | 0,350 | 0,266 |
| MiniLM dense | full_question | 0,250 | 0,550 | 0,385 |
| E5 dense | full_question | 0,200 | 0,400 | 0,279 |

Значения в таблице объединяют все 40 вопросов и служат описанием замера. Для выбора конфигурации используются dev-результаты: у MiniLM dense `evidence_recall@5=0,733`, у MiniLM hybrid `0,667`, у E5 dense `0,467` для clean_query. Поэтому текущий MiniLM dense сохраняется; более высокий общий Hit@5 гибрида не является основанием подбирать настройки по test.

На test-разбиении MiniLM dense Hit@5 составляет **0,44** (25 вопросов, clean_query). Это заметное ограничение. Набор небольшой и использовался в прежних прогонах, поэтому не считается новой независимой слепой проверкой. Нужны дополнительные документы, ручная проверка эталонов и отдельные эксперименты с чанкингом/ранжированием.

Hit@5=0,55 означает наличие хотя бы одного размеченного доказательства в первой пятёрке в 55% этих вопросов. Это не 55% правильных ответов всего агента. Для составного вопроса дополнительно нужно покрытие всех необходимых доказательств. Оценки OCR, маршрутизации и ответа здесь не измеряются.

Новые загрузки используют токеновые окна, тогда как исходный baseline сохраняет прежние окна по 110 словам с перекрытием 28. Эти метрики нельзя автоматически переносить на новую базу. Для неё реализован отдельный [снимок корпуса и ручная разметка](../eval/data/managed/README.md): фиксируются версии, SHA оригиналов, точные контексты, локаторы, настройки и превышение токенового лимита.

## Исправленные ошибки передачи

Открытая страница больше не вытесняет полезный найденный фрагмент, если его нет в переданном тексте страницы или страница обрезана. Источники разных версий не объединяются по одному номеру страницы. Цитаты выдаются как точные подстроки, с локаторами и выбранными ID; неиспользованные блоки не выдаются за подтверждение утверждения. При отбрасывании части утверждений проверкой ответ не объявляется автоматически полным.

Выбор документов и запрет веба выполняются кодом независимо от плана модели. `read_web` принимает только URL, уже полученный в этом запросе. Это ограничения исполнения; выбор содержательно полезного действия всё ещё нужно проверять с настоящей моделью.

## Что остаётся локальной проверкой

GigaChat: авторизация, доступная модель, все используемые JSON-схемы, смысл и полнота ответов, задержки, токены и живой eval. Tavily: актуальные результаты, квоты и чтение реальных страниц. Проверка обновления PDF: реальные ответы EIA/Банка России. Docker: сборка и запуск на Mac/ARM64. GitHub CI добавляет отдельную Linux-проверку; её результат нельзя выдавать за запуск на ноутбуке.

Стенд остаётся однопользовательским прототипом. OCR сложных таблиц, автоматический поиск новых выпусков, распределённая очередь, права доступа и независимая экспертная оценка не объявляются завершёнными.
