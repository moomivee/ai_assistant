# Как оценивается система

Eval разделён на три самостоятельных вопроса: куда пошёл агент, нашёл ли нужный контекст и насколько хорош итоговый ответ. 

## Набор данных

`eval/data/cases.jsonl` содержит 100 авторских seed-вопросов:

| Категория | Количество |
|---|---:|
| Ответ только по отчётам | 40 |
| Корректный прогноз | 15 |
| Уточнение параметров | 10 |
| Свежие данные из веба | 15 |
| Сочетание отчёта и веба | 10 |
| Вне специализации | 5 |
| Ложные предпосылки и попытки изменить правила | 5 |

Для 40 вопросов указаны эталонные фрагменты: ID отчёта, физическая страница и дословная цитата. Для двух вопросов нужны два фрагмента. Цитаты проверяются по реальным PDF. `validate-data` проверяет существование цитат, уникальность вопросов/ID и отсутствие разделения одной группы между dev/test.

У каждого вопроса есть историческая ожидаемая последовательность инструментов, запрещённые инструменты, намерение, проверяемые поля плана, допустимые статусы и рубрика ответа. Для веба разрешён `partial`: отсутствие подтверждённых публикаций должно приводить к ограничению.

Группы связывают близкие вопросы об одном факте, в том числе report/mixed/adversarial. Сплит детерминирован по хешу group: сейчас 33 dev и 67 test, retrieval-подмножество — 15 dev и 25 test. Набор небольшой, содержит только два отчёта и подготовлен с участием AI. Независимая экспертная разметка помечена `human_review=pending`. Это начальный benchmark.

`eval/build_seed.py` позволяет воспроизвести набор.

## 1. Качество поиска

```bash
uv run python -m eval.run validate-data
uv run python -m eval.run retrieval --models e5-small minilm-multi --output .cache/eval/retrieval-v1.json
```

Оба эмбеддера получают одинаковые PDF, разбиение и вопросы. Сравниваются два варианта: `clean_query` — подготовленный информационный вопрос без инструкции об источниках, `full_question` — полный пользовательский ввод. 

| Метрика | Что проверяет | Почему нужна |
|---|---|---|
| hit@1 | Есть ли эталонная цитата в первом фрагменте | Насколько полезен самый вероятный результат |
| hit@5 | Есть ли хотя бы один эталонный фрагмент в первых пяти | Находит ли поиск основание для ответа при небольшом бюджете контекста |
| MRR@10 | Обратный ранг первого релевантного фрагмента, иначе 0 | Различает попадание на первом, третьем и десятом месте |
| evidence recall@5 | Доля независимых нужных цитат, покрытых top-5 | Отражает полноту ответа на составные вопросы |

Релевантность определяется по отчёту, странице и включению нормализованной цитаты в текст чанка. Одна цитата в двух перекрывающихся окнах не увеличивает recall. Размерность эмбеддингов и cosine scores разных моделей напрямую не сравниваются.

В результатах сохраняются per-case ранжирования, chunk ID, scores, длительности, ревизии/хеши моделей через fingerprint, хеши корпуса, датасета, кода и uv.lock. Средние публикуются вместе с `n`. 

## 2. Маршрутизация

Быстрый тест реального LLM-планировщика:

```bash
uv run python -m eval.run routing --split dev --limit 10
```

В режиме `routing` модель реально выдаёт `Plan` и, для `AGENT_MODE=loop`, последующие решения `NextAction`. Затем код применяет валидацию и граф. Но ответы RAG/веба и синтез текста контролируются фикстурами, расчёт прогноза выполняется реально. В трейсах это явно обозначено `eval.controlled_fixture`. Этот режим изолирует ошибки планировщика, не измеряет RAG или качество реальных ответов. Judge в нём запрещён.

В отчёте `initial_plan` сохраняет первый ответ планировщика, а `plan` — фактический план после проверки и возможного повторного извлечения параметров. Маршрутные метрики считаются по последнему; дополнительный LLM-вызов учитывается в `llm_calls`.

Основной критерий маршрута — `tool_policy_pass`: вызваны обязательные инструменты, не вызваны запрещённые, поиск в отчётах предшествует вебу. `required_tool_success` отдельно проверяет успешное исполнение. Чтение страницы и повторный поиск с другой формулировкой допустимы. При чистом численном прогнозе в новом цикле предварительный RAG не обязателен. Запросы, которым инструменты не нужны, проверяются на отсутствие вызовов.

`tool_sequence_exact` оставлен для диагностики прежнего workflow. Дополнительно сохраняются intent, поля плана, количество инструментов и отклонённых действий. Значение 1.0 у `rag_before_web` на запросе без веба само по себе малоинформативно; нужно смотреть per-case маршрут. Реальные запросы retrieval, ранги и их метрики сохраняются на каждом шаге.

## 3. Полный агент и ответ

```bash
uv run python -m eval.run agent --split dev --limit 5 --judge
uv run python -m eval.run agent --split all --judge --output .cache/eval/agent-v1.json
```

`agent` использует реальные инструменты, RAG и настроенную LLM. `--judge` включает второй вызов модели со схемой `JudgeResult`: groundedness, relevance, tone, completeness по шкале 0–4 и объяснение. Judge видит вопрос, рубрику, эталонные контексты (когда они размечены), ответ и использованные источники.

Для judge можно задать `JUDGE_BASE_URL`, `JUDGE_API_KEY`, `JUDGE_MODEL`. Встроенный `--judge` без них использует основную модель; в отчёте это отмечено `judge_same_model`. Это диагностическая оценка, не подтверждённая оценка качества. `task_success_rate` остаётся `null`; некалиброванная оценка обозначается отдельно как `judge_assisted_success_rate`.

Для оценки сохранённых ответов используйте `eval.assess_saved`: он требует явно выбрать отличающуюся модель и сначала проверяет её на пяти контрольных ответах из `eval/data/judge_controls.jsonl`. Если калибровка не пройдена, итоговый success не рассчитывается. Смена размера внутри семейства Qwen не даёт полной независимости. Даже успешная калибровка на пяти примерах не заменяет внешнюю экспертную проверку.

`llm_plan_valid_rate` показывает долю планов по схеме. `response_contract_valid_rate` отражает фактическую валидацию ответа приложением, включая честный `unavailable`. Исключения не прерывают весь прогон: неудачный случай сохраняется и остаётся в знаменателе. Ни статус, ни корректный JSON не доказывают правильность смысла.

## Как использовать трейсы для следующих версий

1. Включить `TRACE_CONTENT=true` для выбранной демонстрационной сессии. Перезапустить приложение. Обычные запросы лучше оставлять без содержимого в логах.
2. Выполнить типовые вопросы и проблемные сценарии; посмотреть план, источники и ошибку в трейсе.
3. Выгрузить кандидатов:

```bash
uv run python -m eval.traces candidates .cache/traces/agent.jsonl .cache/candidates-v1.jsonl
```

4. Независимо проверить ожидаемый маршрут и нужные цитаты по PDF. У кандидата `expected=null`, ответ агента хранится только как `observed_response`. Вручную назначить group/split и сохранить новую версию датасета. Не копировать ошибки агента в эталон.
5. Для существующего набора можно добавить только связь с наблюдаемыми запросами, сохранив разметку:

```bash
uv run python -m eval.traces link eval/data/cases.jsonl .cache/traces/agent.jsonl .cache/linked-v1.jsonl
uv run python -m eval.traces sync-dataset .cache/linked-v1.jsonl --name oil-gas-v2
```

Имена опубликованных датасетов версионируются, существующая версия не перезаписывается. Связанные trace ID остаются в файле и metadata элементов. Текущие 100 вопросов — **seed по требованиям и PDF**. 

## Запуск кнопкой

```bash
uv run python -m eval.ui
```

Откройте http://localhost:8001, выберите режим, сплит, число вопросов и при необходимости judge. Кнопка запускает тот же код `eval.run`, показывает состояние и даёт скачать JSON. Одновременно разрешён один запуск. Сервис предназначен для локального использования.

## Регрессии из пользовательских ответов

В `eval/data/regressions.jsonl` сохранены три примера из присланных ответов локального агента:

- Brent уже указан, но агент просит выбрать сорт. Сохранён ответ API с trace ID.
- Простой прогноз рассчитан, но к нему добавлены требование Tavily и сообщения об отсутствии прогноза, спроса, санкций и других незапрошенных сведений. Сохранён текст из UI; trace ID и исходный план не были предоставлены.
- Сравнение Urals и ESPO: RAG вернул таблицу первой, но модель ответила про ОПЕК+, перепутала ID источника и смысл «до/на». Для этого случая предоставлен полный трейс. В `tests/fixtures/urals_espo_trace.json` сохранены вопрос, план, найденные источники, первый черновик и итоговый ответ; служебные ID HTTP и spans исключены.

Первые два примера — наблюдаемые ответы без полного дерева Langfuse; третий основан на локальном JSONL-трейсе. Для прогнозов обязателен расчёт Brent на 3 месяца без веб-поиска. Исторический workflow предварительно обращался к отчётам; новый цикл может сразу вызвать расчёт. Для сравнения сортов достаточно отчёта. Набор служит для отладки и не считается независимым test-сплитом.

```bash
uv run python -m eval.run agent --data eval/data/regressions.jsonl
```

Запуск требует работающей LLM. HTTP-фикстура в `tests/test_planning.py` отдельно проверяет восстановление пропущенного сорта и фактический вызов расчётного инструмента. `tests/test_forecast_scope.py` использует контролируемые ответы модели: проверяет чистый прогноз, явно запрошенные новости и котировки, ограничение «только отчёты», противоречивые ограничения и ошибки расчёта. Прохождение этих тестов не является замером качества живой Qwen; повторный `agent` eval нужен после обновления локального сервера.

`tests/test_answering.py` воспроизводит реальный плохой черновик, но ответы проверяющего и коррекции в тестах заданы явно. Эти тесты проверяют исполнение защитных правил, а не способность Qwen самостоятельно выдать верный ответ.

После сохранения переносов строк повторно выполнены 160 поисковых запросов: 40 вопросов × 2 эмбеддера × 2 варианта запроса. Ранги и метрики совпали с предыдущим запуском. Проверка сохранена в `eval/results/retrieval-preserve-lines-2026-11-10.json`: изменение представления текста не ухудшило измеренный retrieval на этом наборе.

## Проверка с настоящей моделью

```bash
uv run python -m eval.smoke
```

Команда запускает все три регрессии с настоящими LLM, RAG и инструментами. Проверяет маршрут, статус, параметры плана и наличие размеченных числовых фактов в утверждениях о каждом сорте. Числовое покрытие — узкая проверка этого примера; она не заменяет экспертную оценку смысла ответа. JSON содержит ответы, метрики, версии промптов и кодов. При непрохождении проверок команда завершается с ненулевым кодом, сохранив результат.

В GitHub Actions есть отдельный workflow `live-regressions`: запускается вручную либо для коммита в main с меткой `[live-eval]` в сообщении. Используются Qwen2.5:3b и Qwen2.5:7b в Ollama на CPU с одинаковым контекстом 8192. Ответы и полные локальные трейсы известных учебных вопросов сохраняются в артефакты `qwen-live-regressions` и `qwen7b-live-regressions`. Этот запуск не измеряет скорость на MacBook и не является оценкой на независимом наборе из 100 вопросов.

Первый запуск на CPU сохранён в `eval/results/live-regressions-cpu-timeout-2026-11-10.json`: оба прогноза прошли, а сравнение сортов остановилось по `APITimeoutError` на 120 секундах. Это ограничение исполнения, не завершённый замер качества ответа. Для CPU workflow использует отдельный `LLM_HTTP_TIMEOUT=600`, не увеличивая время ожидания веб-источников.

## Исторический результат workflow

В исходном сравнении фиксированного workflow с 3B и 7B каждая модель прошла два прогноза и не прошла сравнение Urals/ESPO: **2 из 3**. Это не успешное завершение всех требований к качеству ответов. Подробности, исходные ответы и ограничения приведены в [результатах](Results.md#реальный-прогон-qwen-что-получилось).

Промежуточные результаты `live-regressions-*-failure-2026-11-10.json` также сохранены. По реальным трейсам были найдены ошибка разбора диапазона `1.3%-1.5%`, лишние индексы проверяющего и незапрошенные требования к полноте. Для индексов теперь используется схема с точным количеством проверок. `DraftAnswer` запрашивает сначала факты, затем полноту и запрещает свободный список отсутствующих данных. Самопроверка LLM остаётся несовершенной — это видно по последнему ответу 3B.

Числовое покрытие в smoke не доказывает корректность причинных выводов или интерпретации единиц. Нужны просмотр ответа по источнику и независимая экспертная оценка. Прохождение 80 тестов кода не заменяет этот этап.
