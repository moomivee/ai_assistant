# Как оценивается система

Eval разделён на три самостоятельных вопроса: куда пошёл агент, нашёл ли нужный контекст и насколько хорош итоговый ответ. Успешная JSON Schema не означает правильное решение; наличие ссылки не означает, что утверждение следует из источника.

## Набор данных

`eval/data/cases.jsonl` содержит 100 авторских seed-вопросов:

| Категория | Количество |
|---|---:|
| Ответ только по отчётам | 40 |
| Корректный прогноз | 15 |
| Уточнение параметров | 10 |
| Свежие данные из веба | 15 |
| Сочетание отчёта и веба | 10 |
| Вне специализации | 5 |
| Ложные предпосылки и попытки изменить правила | 5 |

Для 40 вопросов указаны эталонные фрагменты: ID отчёта, физическая страница и дословная цитата. Для двух вопросов нужны два фрагмента. Цитаты проверяются по реальным PDF, а не берутся из ответа агента. `validate-data` проверяет существование цитат, уникальность вопросов/ID и отсутствие разделения одной группы между dev/test.

У каждого вопроса есть ожидаемая последовательность инструментов, запрещённые инструменты, намерение, проверяемые поля плана, допустимые статусы и рубрика ответа. Для свежего веба разрешён `partial`: отсутствие подтверждённых публикаций должно приводить к честному ограничению, а не выдуманному ответу.

Группы связывают близкие вопросы об одном факте, в том числе report/mixed/adversarial. Сплит детерминирован по хешу group: сейчас 33 dev и 67 test; retrieval-подмножество — 15 dev и 25 test. Набор небольшой, содержит только два отчёта и подготовлен с участием AI. Независимая экспертная разметка помечена `human_review=pending`. Это начальный benchmark, не репрезентативная оценка промышленного качества.

`eval/build_seed.py` позволяет воспроизвести набор. После ручной разметки не запускайте его поверх новых данных: новую версию сохраняйте отдельным JSONL. Изменение корпуса или вопросов меняет условия сравнения.

## 1. Качество поиска

```bash
uv run python -m eval.run validate-data
uv run python -m eval.run retrieval --models e5-small minilm-multi --output .cache/eval/retrieval-v1.json
```

Оба эмбеддера получают одинаковые PDF, разбиение и вопросы. Сравниваются два варианта: `clean_query` — подготовленный информационный вопрос без инструкции об источниках; `full_question` — полный пользовательский ввод. `clean_query` не является результатом живой LLM-маршрутизации: качество фактического `rag_query` надо оценивать отдельно в полном проходе.

| Метрика | Что проверяет | Почему нужна |
|---|---|---|
| hit@1 | Есть ли эталонная цитата в первом фрагменте | Насколько полезен самый вероятный результат |
| hit@5 | Есть ли хотя бы один эталонный фрагмент в первых пяти | Находит ли поиск основание для ответа при небольшом бюджете контекста |
| MRR@10 | Обратный ранг первого релевантного фрагмента, иначе 0 | Различает попадание на первом, третьем и десятом месте |
| evidence recall@5 | Доля независимых нужных цитат, покрытых top-5 | Отражает полноту ответа на составные вопросы |

Релевантность определяется по отчёту, странице и включению нормализованной цитаты в текст чанка. Одна цитата в двух перекрывающихся окнах не увеличивает recall. Размерность эмбеддингов и cosine scores разных моделей напрямую не сравниваются.

В результатах сохраняются per-case ранжирования, chunk ID, scores, длительности, ревизии/хеши моделей через fingerprint, хеши корпуса, датасета, кода и uv.lock. Средние публикуются вместе с `n`. По одному маленькому test-сплиту нельзя доказывать устойчивое превосходство эмбеддера. Результаты этой итерации уже просмотрены, поэтому будущие изменения потребуют новой отложенной выборки.

## 2. Маршрутизация

Быстрый тест реального LLM-планировщика:

```bash
uv run python -m eval.run routing --split dev --limit 10
```

В режиме `routing` модель реально выдаёт `Plan`, затем код применяет валидацию и граф. Но ответы RAG/веба и синтез текста контролируются фикстурами; расчёт прогноза выполняется реально. В трейсах это явно обозначено `eval.controlled_fixture`. Этот режим изолирует ошибки планировщика, не измеряет RAG или качество реальных ответов. Judge в нём запрещён.

Метрики: точное совпадение порядка инструментов; доля вызванных обязательных инструментов; наличие запрещённого вызова; RAG раньше веба; правильное намерение и поля плана. Для запроса без ожидаемых инструментов лишний вызов считается ошибкой. `forbidden_tool_violation` должно снижаться, остальные показатели — расти. `rag_before_web` считается также на запросах без веба, поэтому его надо читать вместе с per-case результатами и точностью маршрута.

## 3. Полный агент и ответ

```bash
uv run python -m eval.run agent --split dev --limit 5 --judge
uv run python -m eval.run agent --split all --judge --output .cache/eval/agent-v1.json
```

`agent` использует реальные инструменты, RAG и настроенную LLM. `--judge` включает второй вызов модели со схемой `JudgeResult`: groundedness, relevance, tone, completeness по шкале 0–4 и объяснение. Judge видит вопрос, рубрику, эталонные контексты (когда они размечены), ответ и использованные источники.

Для независимого judge задайте `JUDGE_BASE_URL`, `JUDGE_API_KEY`, `JUDGE_MODEL`. Без них используется основная модель, что создаёт риск самооценки; в отчёте фиксируется `judge_same_model`. Сбой judge записывается отдельно, а `judge_coverage` показывает долю реально оценённых ответов. Ошибка оценщика не превращается в нулевой балл ответа.

`llm_plan_valid_rate` показывает долю планов, полученных по схеме. `response_contract_valid_rate` отражает валидацию финального ответа приложением, включая честный `unavailable`; это **не** доля корректных ответов LLM. Семантические ошибки учитываются маршрутными метриками и judge. Субъективные оценки judge требуют выборочной ручной проверки; их нельзя представлять как объективную истину.

При включённом Langfuse метрики прикрепляются к trace ID как scores. Частичные строки сохраняются по мере обработки в соседний `.jsonl`; итоговый `.json` создаётся после завершения. Для повторного опыта нужен новый путь, чтобы не перезаписать предыдущий результат.

## Как использовать трейсы для следующих версий

1. Включить `TRACE_CONTENT=true` для выбранной демонстрационной сессии. Перезапустить приложение. Обычные запросы лучше оставлять без содержимого в логах.
2. Выполнить типовые вопросы и проблемные сценарии; посмотреть план, источники и ошибку в трейсе.
3. Выгрузить кандидатов:

```bash
uv run python -m eval.traces candidates .cache/traces/agent.jsonl .cache/candidates-v1.jsonl
```

4. Независимо проверить ожидаемый маршрут и нужные цитаты по PDF. У кандидата `expected=null`, ответ агента хранится только как `observed_response`. Вручную назначить group/split и сохранить новую версию датасета. Не копировать ошибки агента в эталон.
5. Для существующего набора можно добавить только связь с наблюдаемыми запросами, сохранив разметку:

```bash
uv run python -m eval.traces link eval/data/cases.jsonl .cache/traces/agent.jsonl .cache/linked-v1.jsonl
uv run python -m eval.traces sync-dataset .cache/linked-v1.jsonl --name oil-gas-v2
```

Имена опубликованных датасетов версионируются; существующая версия не перезаписывается. Связанные trace ID остаются в файле и metadata элементов. Текущие 100 вопросов — **seed по требованиям и PDF**, а не 100 собранных пользовательских диалогов. Реальный trace-derived набор должен появиться после живого прогона и ревью.

## Запуск кнопкой

```bash
uv run python -m eval.ui
```

Откройте http://localhost:8001, выберите режим, сплит, число вопросов и при необходимости judge. Кнопка запускает тот же код `eval.run`, показывает состояние и даёт скачать JSON. Одновременно разрешён один запуск. Сервис предназначен для локального использования; без аутентификации выставлять его наружу не следует.
