# Логи, трейсы и версии промптов

Логи отвечают на вопрос «что произошло с сервисом», трейсы — «какие шаги привели к конкретному ответу». Оба слоя используются вместе.

## Логи

JSON-события пишутся в stderr через стандартный Python logging: запуск/остановка API, HTTP-маршрут, код ответа, длительность, запрос к провайдеру, создание индекса, завершение инструмента, отказ валидации, ошибка LLM. В логах есть request ID. Содержимое вопроса, ключи и тело HTTP-запроса не выводятся.

HTTP ID возвращается заголовком `X-Request-ID`; отдельный `trace_id` находится в ответе агента и в раскрывающемся блоке UI. В корневом трейсе сохраняется связь с HTTP ID. Это позволяет найти конкретный проход без записи пользовательского текста в обычный лог.

## Настройка Langfuse

В проекте используется закреплённая через uv.lock ветка SDK 3.x. Native `CallbackHandler` подключается в config вызова LangGraph. Внешний OpenAI SDK не является LangChain chat model, поэтому LLM-вызовы дополнительно обёрнуты в generation observations; инструменты Ouroboros и эмбеддеры также имеют собственные spans.

В своём проекте Langfuse создайте API keys и заполните `.env`:

```dotenv
LANGFUSE_ENABLED=true
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_BASE_URL=https://cloud.langfuse.com
TRACE_FILE=.cache/traces/agent.jsonl
TRACE_CONTENT=false
```

Для своего сервера или другого региона замените base URL. Ключи не коммитятся. Отсутствие ключей не останавливает локальное приложение; в логе появится причина отсутствия внешней трассировки.

`TRACE_CONTENT=false` исключает input/output из локального JSONL и маскирует их в Langfuse. Остаются имена шагов, статусы, длительности, версия промпта и сведения о расходе токенов. Для анализа конкретного учебного диалога и формирования eval-кандидатов временно включите `TRACE_CONTENT=true`; тогда текст вопросов, ответы и найденные фрагменты попадут в настроенный Langfuse и локальный файл.

Локальные span ID и ID наблюдений SDK не совпадают; для сопоставления используется общий trace ID. Родительские связи поддерживаются внутри каждого представления. Native callbacks показывают LangGraph и его узлы, явные spans — внутреннюю работу узла; это объясняет два уровня в дереве.

## Что проверить в интерфейсе

1. Запустить приложение с корректной LLM и ключами Langfuse.
2. Спросить про Sokol только по отчёту; затем задать свежую котировку, прогноз и запрос с отсутствующим дисконтом Urals.
3. В Langfuse открыть Traces и найти `trace_id` из UI приложения.
4. Убедиться, что корень `agent.request` содержит LangGraph, узлы workflow, generation для plan/answer и фактически выполненные инструменты.
5. Проверить: RAG предшествует вебу; прогноз есть только в соответствующем сценарии; уточнение не вызывает расчёт; generation содержит модель, token usage и prompt version.
6. При включённом содержимом открыть вход/выход проблемного шага. Сравнить увиденный план и ссылки с ответом приложения.
7. После agent eval открыть scores у тех же trace ID.

Автоматический тест `tests/test_langfuse_export.py` использует реальный SDK и native callbacks с локальным OTLP-приёмником. Он проверяет экспорт, иерархию, общий trace ID и маскирование. Он не проверяет отрисовку веб-интерфейса Langfuse. Живая проверка этого интерфейса пока не выполнена.

## Промпты

Три промпта хранятся в `prompts/`: план, доказательный ответ, judge. При локальном использовании в трейс записывается SHA256 текста. Чтобы создать версии в Langfuse:

```bash
uv run python -m src.cli publish-prompts --label staging
```

Затем проверить staging-версию на dev-наборе, назначить удачной версии метку production в интерфейсе Langfuse и включить:

```dotenv
PROMPT_SOURCE=langfuse
PROMPT_LABEL=production
```

`PROMPT_LABEL=staging` позволяет оценивать кандидата до продвижения. При недоступности сервера используется локальный файл с записью fallback в лог. Модель, версия промпта и датасет должны фиксироваться вместе с результатом eval.

Это управляемая история промптов, а не автоматическое самообучение Ouroboros. Промпты не меняются по собственному решению агента.

## ONNX Runtime

Телеметрия ONNX Runtime отключается переменной `ORT_DISABLE_TELEMETRY=1` до импорта нативной библиотеки, а также API-вызовом `disable_telemetry_events()`. Docker задаёт переменную заранее. Это отдельная телеметрия библиотеки, не Langfuse.

Официальные материалы: [structured outputs Ollama](https://docs.ollama.com/capabilities/structured-outputs), [Langfuse и LangGraph](https://langfuse.com/integrations/frameworks/langchain), [политика ONNX Runtime и отключение телеметрии](https://github.com/microsoft/onnxruntime/blob/main/docs/Privacy.md). Примеры в текущей документации Langfuse могут относиться к более новой ветке SDK; проверяйте совместимость с `uv.lock` проекта.
