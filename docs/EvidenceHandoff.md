# Передача найденных источников в ответ

Проверка от 11 ноября 2026 года, ветка `review/agent-eval-20261110`.
Изменения относятся к агентскому циклу, `main` не изменён.

## Причина сбоя

В пользовательском запросе о плотности и сере Urals и ESPO первый поиск уже
вернул таблицу EIA с обеими характеристиками. Проблема находилась после retrieval:
источники сохранялись и передавались следующему выбору действия, но подготовка
ответа ожидала отдельного решения модели `finish`. Вместо него модель продолжала
поиск, пока не закончился общий бюджет. Найденный фрагмент так и не стал ответом.

Это не потеря текста при HTTP-передаче в Ollama, а неверный переход между
этапами агента. Контрактный тест через настоящий OpenAI SDK и HTTP-фикстуру
проверяет, что исходный текст таблицы и адрес `R1:B1` присутствуют во входе
генерации. Реальные ответы модели проверены отдельно.

## Что изменено

- Первый поиск выполняется по `rag_query` из проверенного `Plan`, когда приоритет
  отчётов оставляет только одно допустимое действие. Лишний LLM-вызов для выбора
  единственного инструмента убран. Этот шаг отмечен `origin=plan_policy`;
  последующий выбор действий моделью сохраняется и отмечается `origin=llm`.
- После инструмента новый набор источников сразу поступает в `agent.answer`.
  Если ответ полон и обязательные действия выполнены, запрос завершается.
  Если неполон, модель получает подготовленную часть в `current_answer` и может
  продолжить поиск или открыть страницу. Возможность выбирать действия сохранена.
- Поле `source_ids` у поискового решения не отбрасывает случайно найденный текст.
  Явный выбор поднабора учитывается только при `finish`.
- Повтор без нового контекста не запускает ту же генерацию заново. Частичный
  ответ сохраняется при последующей ошибке или остановке.
- Внутри общего бюджета 180 секунд оставлен резерв 60 секунд для ответа.
  Поисковые этапы используют предел 120 секунд; ответ может использовать всё
  оставшееся общее время. Это кооперативный бюджет, не жёсткое прерывание процесса.
- Схема ответа сокращена до `claims` и `complete`. Промпт требует сведения по
  всем запрошенным характеристикам, единицы и вывод сравнения. Уточнены общие
  отраслевые термины и обратное соотношение °API и физической плотности.
  Названия сортов и значения из тестового вопроса в промпт не подставлены.
- В планировании `clarify` применяется только к недостающим параметрам расчёта,
  как и предусмотрено контрактом. Пересказ обычного исследовательского вопроса
  в этом поле больше не блокирует поиск. Необходимые уточнения прогноза сохранены.
- В JSON и интерфейсе появился `answer_checks`: после какого инструмента,
  с какими источниками и за какое время формировался ответ, сколько утверждений
  прошло проверку. Это диагностика передачи и проверки, не оценка истинности.

## Проверка настоящей Qwen

Использованы Ollama, `qwen2.5:3b` и отдельная проба `qwen2.5:7b` на CPU
GitHub Actions: контекст 8192, temperature 0, локальные промпты,
самопроверка той же моделью отключена. Для 3B использован бюджет 180/60 секунд
(общий/резерв ответа), для 7B — 300/120 секунд.
Условия, версии промптов, ответы и временные измерения сохранены в JSON.
Измерения CPU Actions не являются прогнозом скорости на MacBook.

Проверки разделены на два вида:

1. Прямая передача одного и шести сохранённых публичных фрагментов в генерацию.
   Здесь источник контролируется, но ответ пишет настоящая Qwen.
2. Полный проход от вопроса: настоящие планирование, поиск по PDF, инструменты
   и генерация. Дополнительно используются вымышленные данные с переставленными
   значениями; только в этих контрольных сценариях результаты инструментов заданы.

полные ответы, а не только зелёный статус CI.

У 3B узкая проверка в `810e4fd` засчитала 3/6 случаев, но один из них был ложным
успехом: выдуманные значения отсутствующего сорта сопровождались ожидаемым
статусом `partial`. Критерий исправлен в `handoff-v3`: для этого случая обязательны
пустые `claims`. Отдельный тест показывает, что выдуманные утверждения больше не
проходят такую проверку. Это изменение eval, не правило ответа, встроенное в агента.

## Воспроизведение

При работающей Ollama, установленном окружении и подготовленном индексе:

```bash
uv run python -m pytest -q
uv run python -m eval.handoff --output .cache/eval/handoff-local-probe.json
uv run python -m eval.handoff --suite --output .cache/eval/handoff-local-suite.json
```

Для нового измерения используйте новое имя файла. Набор
`eval/data/handoff.jsonl` содержит шесть целевых регрессий, включая
переформулировку, отсутствие данных, прогноз и выход за специализацию.
Это **dev-набор**, который используется при отладке, а не независимый test.

`--suite` проверяет маршрут, статус и размеченные числовые факты, затем выполняет
три синтетических сценария. Числовое покрытие не проверяет направление сравнения
и правильность перевода терминов. Синтетические ответы также нужно читать:
изменившийся текст сам по себе не доказывает корректную работу с контекстом.

Полный живой eval на 100 вопросах и независимая экспертная оценка ещё не проведены.
Правильный ответ на известный вопрос не даёт гарантии для произвольных вопросов.
Ссылки и проверка присутствия чисел не доказывают, что число отнесено к нужному
объекту и правильно интерпретировано. Общие ограничения описаны в
[Limitations](Limitations.md).
