# Выбор действий, прогресс и остановка

Изменения относятся к ветке `review/agent-eval-20261110` и режиму `AGENT_MODE=loop`.
Прежний `workflow` сохранён для сравнения. Ответы на отдельные вопросы не записаны
в контроллер: запросы и следующие действия по-прежнему выбирает LLM.

## Какая проблема исправляется

В пользовательском запуске сравнения Urals и ESPO было шесть решений, но только
два исполненных инструмента: поиск и чтение страницы. Остальные попытки повторяли
те же аргументы. Прежняя политика после повтора исключала целый тип инструмента,
когда были доступны другие. Это мешало изменить поисковую формулировку и могло
подталкивать к чередованию уже выполненного поиска и уже прочитанной страницы.

Теперь отклоняется одинаковый вызов, а изменённый запрос остаётся доступен.
Регистр, повторные пробелы и эквивалентная Unicode-запись запроса не обходят проверку.
Повтор содержит `duplicate_of` и `reused_source_ids`: модель видит, где уже получен
результат. Источники сохраняются в состоянии одного запроса.

## Что получает модель

Первый поиск по отчётам использует `rag_query` из проверенного `Plan`, если это
единственное разрешённое первое действие. Дополнительный вызов LLM для выбора
единственного инструмента не нужен. В диагностике этот шаг отмечен
`origin=plan_policy`. При нескольких допустимых действиях и на следующих шагах
выбор делает модель (`origin=llm`).

После инструментов новый набор источников сразу поступает в `agent.answer`.
Отдельное решение `finish` для этого не требуется. При полном ответе и выполнении
обязательных требований запрос завершается; при частичном ответе модель получает
его в `current_answer` и может выбрать следующее действие. Это исправляет случай,
когда нужная таблица уже найдена, но модель тратит весь бюджет на планирование.
Параметр `source_ids` у поискового действия не может случайно отфильтровать
источники: выбор поднабора учитывается только при явном `finish`.

В существующую схему `NextAction` добавлены два поля:

- `evidence_checks`: какие необходимые сведения найдены, с ID их источников;
- `missing_facts`: каких конкретных сведений исходного вопроса ещё не хватает.

Дополнительный вызов LLM для этого не создаётся. Новые поля увеличивают объём
одного ответа модели; влияние на скорость нужно измерить. В следующем шаге
доступны предыдущая оценка, результаты инструментов, оставшиеся шаги и время.
Предыдущая оценка не заменяет исходные тексты.

Если модель сама указала `assessment=enough`, список пробелов пуст, ссылки
существуют и все обязательные действия выполнены, контроллер переводит запрос к
ответу даже при предложении ещё одного инструмента. В JSON сохраняются
`model_action` и `controller_note`. Проверка ссылок не доказывает полноту или
правильность понимания источника. Итоговые утверждения проходят прежнюю проверку
ссылок и чисел; смысловая ошибка всё ещё возможна.

## Когда поиск прекращается

| Настройка | По умолчанию | Что ограничивает |
|---|---:|---|
| `AGENT_MAX_STEPS` | 6 | Число шагов выбора действия, включая первый шаг по правилу, отклонения и завершение |
| `AGENT_NO_PROGRESS_LIMIT` | 2 | Последовательные попытки без нового содержимого или расчёта |
| `AGENT_TIMEOUT_SECONDS` | 180 | Общий кооперативный бюджет обработки запроса, в секундах |
| `AGENT_ANSWER_RESERVE_SECONDS` | 60 | Часть общего бюджета, которую поисковые решения не могут израсходовать |

Первый исполненный инструмент задаёт начальную точку, даже если результат пуст.
Поэтому после первоначального пустого поиска и одного отклонённого повтора
остаётся возможность изменить запрос. Новое содержимое или первый результат
расчёта сбрасывает счётчик. Новая ссылка или ID с тем же текстом этого не делают.
Изменившийся текст с датой учитывается как новый; это простая проверка новизны,
а не смысловой релевантности. Перефразированные дубли могут пройти её.

После достижения порога агент возвращает уже подготовленный ответ; новый набор
источников при необходимости сначала передаётся генерации. Неизменившийся контекст
не вызывает ещё одну генерацию. `stop_reason=no_progress` объясняет остановку; полнота ответа
оценивается отдельно. Если данных нет, агент возвращает `partial`, без
выдуманных фактов. Время инструментов для отклонённых попыток остаётся `null`.

При исчерпании времени новые этапы и обращения к модели не запускаются.
Таймаут LLM, Tavily, FRED и RSS ограничивается оставшимся бюджетом. Завершение
возвращает уже подготовленный проверенный текст, если он есть, и причину
`time_budget_exhausted`. Найденные, но ещё не использованные источники остаются
в диагностике. Их наличие само по себе не превращается в готовый ответ.

Поисковая часть использует отдельный предел внутри общего: по умолчанию 120 секунд.
`research_budget_exhausted` означает, что продолжение поиска остановлено ради
резерва на ответ. Генерация ответа может использовать всё оставшееся общее время,
в том числе до наступления этого предела. Резерв ограничен половиной общего
бюджета, поэтому при очень малом тестовом таймауте не вытесняет планирование целиком.

Это **не жёсткая гарантия HTTP-ответа ровно за 180 секунд**. Синхронная работа с
PDF и эмбеддерами не прерывается посередине; сетевые таймауты применяются к фазам
обмена, а не как убийство фонового процесса. Очередь сервера и отправка телеметрии
тоже могут увеличить время в браузере. Отдельный жёсткий таймер с отменой всей
обработки не реализован. Бюджет не гарантирует прекращение генерации на стороне
внешнего LLM-сервера после разрыва соединения.

## Проверка изменения

`tests/test_agent_progress.py` проверяет повтор поиска и страницы, изменение
запроса при доступных альтернативных инструментах, дубли с новыми URL,
достаточность со ссылками, неизвестные ссылки и обязательную проверку свежести.
Существующий тест сохраняет сценарий «пустой поиск → повтор → изменённый запрос».

`tests/test_request_budget.py` проверяет общий бюджет между этапами и внутри
одного этапа, уменьшение реального таймаута OpenAI SDK, сохранение частичного
ответа и найденных источников. Используются управляемые часы без ожидания.
Браузерная проверка проверяет отображение оценки, повторов и причин остановки.

`tests/test_evidence_handoff.py` проверяет передачу текста и ID через настоящий
OpenAI SDK с HTTP-фикстурой, отсутствие лишнего решения `finish`, продолжение
после частичного ответа и обязательный расчёт в смешанном запросе. Фикстура не
подменяется замером качества модели: для него используется `eval.handoff`.

Это проверки контроллера с заданными ответами модели. Живые диагностические
прогоны `eval.handoff` сохраняют реальные ответы Qwen на одном фрагменте, шести
фрагментах и в полном проходе. Дополнительный набор содержит шесть регрессионных
вопросов; синтетические проверки меняют значения в источнике и моделируют пустой
первый поиск. Исторические результаты в `eval/results` не переписываются.

Для локальной проверки следует повторить исходный вопрос, его переформулировку,
вопрос без ответа в корпусе, чистый прогноз и запрос свежих событий. Оценивать
нужно не только меньшее время, но и фактическую правильность, полноту,
приоритет отчётов и отсутствие преждевременной остановки. Сохраняйте JSON и
Trace ID. Сравнение имеет смысл на одной модели и одинаковых настройках.

Новый прогон существующего набора выполняется командой:

```bash
uv run python -m eval.run agent --data eval/data/audit.jsonl

# Целевой живой прогон передачи источников и регрессий:
uv run python -m eval.handoff --suite --output .cache/eval/handoff-local.json
```

Она требует работающей модели, выполняет все вопросы набора и сохраняет новый
отчёт в `.cache/eval`. Автоматические маршрутные метрики не заменяют проверку
смысла ответа человеком или независимым оценщиком. Полный набор и метрики
описаны в [Evaluation](Evaluation.md).

## Обновление второй локальной копии

В каталоге с улучшенной версией, при отсутствии собственных несохранённых правок:

```bash
cd ~/Projects/ai_assistant_ver_2
git switch review/agent-eval-20261110
git pull --ff-only origin review/agent-eval-20261110
docker compose -p ai_assistant_ver_2 -f compose.yaml -f compose.local.yaml up --build -d
```

При `PORT=8002` стенд будет на http://localhost:8002. Ключи в `.env` сохраняются.
Новые настройки имеют значения по умолчанию даже в прежнем `.env`; для явной
фиксации эксперимента можно добавить:

```dotenv
AGENT_MODE=loop
AGENT_NO_PROGRESS_LIMIT=2
AGENT_TIMEOUT_SECONDS=180
AGENT_ANSWER_RESERVE_SECONDS=60
PROMPT_SOURCE=local
```

При удалённых промптах Langfuse нужно отдельно обновить `decide` и `cited_answer`.
`LLM_HTTP_TIMEOUT=600` не отменяет общий бюджет в 180 секунд. Если модель работает
медленно, увеличение общего бюджета позволит исследовать завершённый ответ,
но не устранит повторные действия или смысловые ошибки. Первая копия проекта и
ветка `main` для этой проверки не изменяются.
